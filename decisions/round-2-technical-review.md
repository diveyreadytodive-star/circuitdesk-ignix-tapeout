Date: 2026-09-30 (Asia/Seoul). Participants: leader, platform agent A, product/UI agent B, strategy/QA agent C. This is an integration review of evidence and remaining gates, **not** a deployment approval or a claim of hackathon eligibility.

- The TapeOut frontend bundle [`index-CMTeTi9V.js`](https://tapeout.net/assets/index-CMTeTi9V.js) presents an X Layer test-phase warning that contracts are **not sealed and have not been independently audited**. This warning must be visible near any real spend/signature and in public limitations.

The fork created a synthetic processor, minted 4 NAND, taped XOR circuit #1, observed the 4 units consumed, matched netlist readback, rejected a wrong fee, and evaluated `[0,1,1,0]`. The script refuses a non-Anvil endpoint and uses an unlocked synthetic account. These transactions and hashes are **local fork artifacts**, not a CircuitDesk mainnet launch.

## Review findings and objections

1. **Supported execution is narrower than “general compute.”** An existing XOR circuit demonstrably evaluates by a read-only chain call. We may describe that exact behavior as `eth_call` evaluation. It has no transaction receipt and should not be confused with the separate paid tapeout transaction. Do not imply any arbitrary user program, general runtime, or automatic policy enforcement.
2. **Creation path is high consequence.** The app may require a processor creation fee, transistor mints at `mintPrice × deficit + protocolFee`, and tapeout fee, plus gas. The user must see a fresh quote, contract destination, chain, and max spend before each wallet signature. The observed `0.0066 OKB` factory fee is a block-specific read, not a promised fixed price.
3. **Client bundle versus contract authority.** The live client supplies the intended ABI/flow; the factory proxy and live reads corroborate deployment. The guarded local fork now validates the concrete create→mint→tapeout→readback→eval path, including event decoding. This still does not audit contract source, eliminate upgradeability risk, or prove a user wallet will see identical future state. Because the factory is upgradeable and unsealed, final writes must recheck address, code/state, and amounts immediately before signing.
4. **No own launch proof yet.** The existing 256 processors and XOR sample demonstrate platform capability, not CircuitDesk eligibility. A processor created by the user's wallet, disclosed issuance settings at deployment, and a circuit taped out on that processor before the deadline remain mandatory.
5. **UX contract.** B’s screens must label local truth table, read-only onchain evaluation, pending transaction, confirmed tapeout receipt, and failed/rejected transaction as distinct states. An explorer link is shown only after a real hash and confirmation. A read-only result must not be labeled “taped out by CircuitDesk.”
6. **Issuance needs a reason beyond a round number.** A proposed 100,000 NAND+LATCH total supply cap and 0.000066 OKB/unit, the minimum suggested in the observed L2 UI. A 4-NAND starter XOR would require 4 units. At block-specific observed values, processor creation `0.0066 OKB` + one mint `(4 × 0.000066 + 0.00066) OKB` + tapeout `0.0013 OKB` totals **0.008824 OKB plus gas**, across three wallet signatures. This is a review quote, not a fixed future charge or authorization to transact. Supply cap and unit price appear fixed after processor creation; confirm in the exact transaction and readback. A cap of 10,000 would allow at most 2,500 four-NAND XOR circuits but could be bought out for about `0.66 OKB` plus fees at the proposed unit price; 100,000 would allow more headroom and cost roughly `6.6 OKB` plus fees to exhaust. Those are theoretical ceilings, not demand forecasts. If third parties can mint freely, either cap can be hoarded or exhausted, and CircuitDesk cannot reserve inventory or promise availability.

## Decision

Keep the guided Boolean-template lab and public passport. Add **read-only onchain evaluation** only for actual circuit IDs through the verified processor ABI, explicitly labeled `eth_call`. Preserve the local preview for preflight and compare its truth table to a real existing circuit during verification. The direct wallet flow remains gated until encoder, cost calculation, event decoding, chain guard, and error states pass tests against live reads and a local fork. Mainnet write transactions remain user-signed.

**Dissent / unresolved risk:** C considers bundle-derived write semantics and unaudited upgradeable contracts insufficient grounds to imply safety. The leader and A retain a wallet-based write path because actual factory deployment/tapeout is mandatory for entry, with preflight disclosures and no autonomous signing. B should not hide this limitation in a README only.

**Economics recommendation, not yet a deployed choice:** 100,000 cap is more defensible than 10,000 for an open novice workbench because it reduces cheap supply exhaustion and supports repeat use. Do not describe the high ceiling as circulation, traction, intentional scarcity, or projected adoption. The final deployment values require a fresh contract/UI quote and user review immediately before the wallet action; once deployed, record the exact immutable settings in the README and form.

## Cross-review feedback and changes made

- **B to A and leader:** A simple `gateCount × unitPrice` card would hide the protocol mint fee, tapeout fee, existing NAND balance, gas, and a possible **partial state** if mint succeeds but tapeout fails. B changed the preflight to call `estimateTemplateCost`, show held/to-mint units, component value, protocol fee, tapeout fee, total excluding gas, and the number of wallet actions. B also mapped adapter status objects into explicit mint versus tapeout progress; a successful mint is not called a successful circuit tapeout.
- **A to B and leader:** A public reference XOR result in the same evidence space as our future project receipt could look like our deployment. A requested a separate “protocol reference, not our project” panel and a project receipt area that stays “not deployed” until onchain verification. B's implementation is to be checked in Round 3 rather than assumed from this request.
- **C to A/B:** C independently read the live adapter and identified stale fee risk after a mint, saved hashes being restored as confirmed without chain recheck, an adapter 200-character story limit versus UI 500, and a UI that could not evaluate our own newly taped circuit. A pinned the factory EIP-1967 implementation before writes, added a post-mint tapeout-fee read and `verifyReceipt` for saved hashes; B aligned the story length and added an own-circuit read path. C tested `verifyReceipt` against synthetic local-fork processor and circuit transactions; both returned verified. Browser end-to-end behavior still needs Round 3 inspection.
- **Residual risk all three retained:** An upgrade or fee change can occur between a final preflight and mining. A user can be left with confirmed paid mints even if a later tapeout fails or is rejected. The frontend contract warning remains test-phase, unsealed and unaudited; no team member claims these checks make a mainnet transaction safe or reversible.
